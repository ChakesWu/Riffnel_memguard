1　项目概述

一句话定位：Riffnel_memguard 不存储记忆。它接在现有智能体记忆库（Mem0 等，或自研存储）之上，在智能体答错时查出是哪条记忆导致、为什么错；生成可审批、可回滚的修正方案；再用可重现的测试验证「错误已消失、没有引入新错误」，并输出带校验链的证据报告。可以理解为记忆的「事故调查 + 修正验收」层。

要解决的问题智能体的长期记忆会出错，并且错误跨会话持续影响回答：权威来源（制度、产品条款）更新后记忆仍是旧版本；删除请求只删了原始记录、摘要里仍有残留；记忆被写入恶意指令等。现有项目多解决「怎么存、怎么取、怎么防写入」，出事之后「如何定位责任记忆、受控修正、并证明修正有效」仍缺少完整流程。
我们做了什么溯源链接（记忆 → 条款版本）、事故调查与六类错误归因（M1–M6）、非破坏性修正（预演、审批、应用、回滚）、验证（重放、回归、残留探测）、证据报告、记忆体检与来源更新后的重新验证；提供命令行、Web 界面与 Python 接口。
当前状态v0.1 预览，已可运行：约 2500 行 Python 核心代码，52 项自动化测试，持续集成（Python 3.10、3.12、容器镜像）通过。适配器：JSON、SQLite、Mem0；另可导入 memwall 扫描结果。
验证情况仿真基准 74 个用例；并在真实堆栈上验证（Mem0 + 本地向量库 + Pydantic AI 智能体 + DeepSeek 语言模型 + 真实中文嵌入模型）：条款过期场景在修复回归检查方式后 10 次全部通过（修复前为 6/10，过程见第 9 节），删除残留场景 5 次全部通过。样本小、数据为仿真，详见第 9 节及其限制。
一个真实发现在 Mem0 开源版 2.2.1 上实测：用它自带的 delete 删除一条记忆后，被删文字的完整内容仍保留在其历史库（history.db）中。本项目把这类残留纳入探测并清除。
开源与合规Apache-2.0；包含贡献指南、行为准则、治理、安全政策、路线图、更新日志与第三方许可证清单；默认离线运行、无遥测。
与同类项目的关系溯源、审计、来源漂移检测、回滚、残留检查，现有开源项目各自已有一部分（第 7 节逐项核实）。本项目的差异是把它们组合为面向事故的「调查、修正、验证」流程，并以带有效期的条款版本为基准；这是组合创新，不是单项技术的首创。

2　背景与痛点

2.1　智能体记忆成为新的故障来源

带长期记忆的智能体（客服、助手、业务流程智能体）把对话中的事实、摘要、偏好写入记忆库，之后跨会话取用。记忆一旦出错，错误会反复出现，且不会像一次提示词错误那样「重启即消失」。常见的错误来源有六类：

  • 权威来源更新后，记忆里仍是旧版本（过期）；
  • 同一事项存在互相矛盾的多条记忆（冲突）；
  • 属于 A 用户、A 产品、A 地区的记忆被用在 B 身上（串用）；
  • 没有来源依据的内容被写进记忆，例如模型自行概括或幻觉（无来源写入）；
  • 用户要求删除的个人信息，原始记录删了，摘要、向量或历史库里仍有残留（应删未删）；
  • 被注入的恶意内容写进记忆（投毒）。

2.2　两个典型事故（本项目的演示场景，数据为仿真）

场景经过
过期（M1）某银行信用卡「金卡免年费」条件由每年刷满 3 笔改为 6 笔（2026-07-01 生效）。智能体仍从旧记忆取值，对客户答「3 笔」。需要查出是哪条记忆、是否还有依赖它的摘要、改什么、改完如何证明。
应删未删（M5）客户要求删除手机号。原始记录已删除，但一条回访摘要里仍写着号码，智能体被问到时照样说出。

2.3　一个真实框架里的残留

我们在 Mem0 开源版 2.2.1 上实测：Memory.delete 只删除活动记忆，被删文字的完整内容（新增、更新、删除三类记录）仍保留在它的 SQLite 历史库中。也就是说，即便「调用了删除接口并返回成功」，数据仍可能留在同一套框架的另一张表里。这类残留需要被主动探测，而不能默认删除成功。

2.4　行业与合规背景

  • 个人信息删除。《中华人民共和国个人信息保护法》第四十七条规定了个人信息处理者应当主动删除个人信息的情形，以及个人请求删除的权利；同时规定了例外（如法定保存期限未届满、删除在技术上难以实现时，应停止存储和必要安全保护以外的处理）。本文据二手资料引用，未逐项核对正式法律文本，引用前应以全国人大或国家法律法规数据库的正式文本为准。来源见附录 B。
  • 记忆与上下文投毒。OWASP 发布的「智能体应用十大风险（2026）」把「记忆与上下文投毒」列为 ASI06。本文据二手资料引用，未直接核对 OWASP 原文。

2.5　现有方案的缺口

现有开源项目已分别覆盖：记忆的存取与去重（如 Mem0）、写入前扫描与隔离（如 memwall）、溯源与审计日志（如 typed-recall、memory-blackbox）、来源漂移检测（如 agentmem、mneme）、删除证明与隔离探测（如 Ferryte，源码可见但非 OSI 开源）。缺口在于：出事之后，以权威来源的版本和有效期为基准，系统化地归因、受控修正、批量回归并出具可审计的证据，且能在离线、可复现、可开源自部署的条件下完成。

3.1　核心思路：调查 → 修正 → 验证

3.2　六类记忆错误与默认修正

代码名称判定信号默认修正
M1过期记忆对应的条款版本在事故发生时已失效停用旧记忆，按现行版本新增，清理派生摘要
M2冲突同一主题、同一作用域有多条有效记忆且取值不同，落败者不是被取代的旧版本来源能裁定则停用落败者；裁定不了则隔离待人工复核
M3串用回答依据的记忆所属作用域与事故作用域不符把记忆改回正确作用域
M4无来源写入记忆陈述规则类事实，取值却对应不到任何条款版本隔离，交人工复核
M5应删未删已受理删除请求，但原始记录、摘要或历史库中仍能找到删除并清理派生与历史残留，再探测
M6投毒含指令性内容（仅基础启发式），或由外部扫描工具标记隔离

多类同时命中时，按「越具体、越可确定越优先」的顺序判定：M5 → M3 → M1 → M2 → M4 → M6。归因的前提是回答中的错误主张能与某条被取用的记忆对上；对不上时，系统给出「无法归因」，说明问题不在记忆层，应转向提示词或模型层处理。

3.3　设计原则

原则含义
非侵入通过适配器接入现有记忆库，只需在检索处记录取用了哪些记忆。
证据优先每个结论都附记忆原文、条款原文、版本、时间与校验值。
非破坏性默认「停用并新增」，保留历史；只有删除请求才物理删除，且审计日志只记录对象 ID 与哈希，不记录被删内容。
人在回路修正方案先预演再审批，审批人写入审计链；未审批不能应用。
离线、确定性默认不联网、无遥测；规则加字符 n-gram 检索；语言模型与真实嵌入器是可选项。
可重现修正前后快照校验值、参数、生效日期写入报告。

4.2　模块与数据

模块职责
溯源链接（Linker）把记忆连到它依赖的条款版本：显式标注（置信度 1.0）、主题键比对（0.9）、语义相似度（取得分）。取值对不上任何版本的记忆列为 M4 候选。并提供影响分析：条款版本 → 记忆 → 派生记忆 → 测试题。
事故调查（Investigator）从回答中抽取主张（数字加单位，支持阿拉伯数字与中文数字），按事故发生时间找出当时有效的条款版本，在被取用的记忆里找出取值相同者，按判定顺序归类并附证据。
修正（Corrector）按类别生成动作（停用、新增、改作用域、删除、清理派生、隔离），支持预演、审批、应用、回滚；每步写入审计链。
验证（Verifier）重放原事故；沿溯源图选出相关测试题批量回归，并检查「修正前通过的题仍通过」；删除请求做残留探测。
残留探测精确（字符串）、变形（全角、空格、连字符、中文数字、邮箱拼写混淆）、行为（让智能体回答探测问题）三层为硬性关卡；语义层只提示「待人工复核」。
审计日志只追加；每条事件带前一条的 SHA-256 哈希，篡改可被检出；只记录对象 ID 与哈希，不记录被删内容。
适配器统一接口：列出、读取、检索、新增、停用、隔离、恢复、删除、改作用域、快照；可选 traces() 暴露存储在活动记忆之外的残留（如 Mem0 历史行）。

4.3　技术栈

Python 3.10 及以上；pydantic（数据模型）、Typer 与 Rich（命令行）、scikit-learn（字符 n-gram TF-IDF 检索）、SQLite（审计日志与参考存储）、Streamlit（界面，可选）、pytest（测试）。可选组件：Mem0（Apache-2.0）、Pydantic AI（MIT）、fastembed（Apache-2.0）及 BAAI/bge-small-zh-v1.5 嵌入模型（Hugging Face 模型页标注 MIT）。第三方依赖的许可证已核实至直接依赖，传递依赖尚未逐项核实（见仓库 THIRD_PARTY_LICENSES.md）。

4.4　部署方式

三种方式均无需联网、无需密钥即可运行演示：（1）pip install -e ".[dev]" 后使用命令行；（2）docker compose up --build 启动 Web 界面（持续集成中已构建镜像并在容器内运行两个演示）；（3）作为 Python 库调用 service 模块。接入真实模型与嵌入器通过环境变量配置，不改代码。

5　关键技术与实现要点

5.1　以条款版本和有效期为基准的归因

条款（如「金卡免年费条件」）带有多个版本，每个版本有取值与有效期区间。事故调查按事故发生的时间而不是「今天」判断当时的有效值，因此同一条旧记忆在 2026-05 的事故中是正确的，在 2026-08 的事故中是过期的（基准集中的「历史有效」用例专门检验这一点）。来源更新后，无需等事故，系统沿溯源链接找出仍依赖旧版本的有效记忆并生成修正方案。

5.2　非破坏性修正与审批

过期记忆被「停用」而不是删除，并新增现行版本、保留取代关系；派生摘要一并清理。方案先以预演（diff）展示将发生的变更；只有审批后才能应用；停用、隔离、新增、改作用域均可回滚，删除不可回滚且会明确提示。已有一条符合来源的记忆时不重复新增。

5.3　删除验证与历史库残留

删除请求的验证不信任「删除接口返回成功」。探测同时检查活动记忆、派生摘要、存储自带的历史行（trace），并让智能体回答探测问题以检查行为层。验证中另用不依赖本项目探测器的方式直接扫描数据目录原始字节，作为独立旁证。语义层在基准中误报较多（见第 9 节），因此只作人工复核提示。

5.4　与真实系统接入

  • Mem0 适配器：读写 Mem0 记忆，修正状态存放在其元数据中；Mem0 默认向外发送匿名遥测，本项目在自带的构造函数中强制关闭。
  • SQLite 适配器：可映射已有表的列名，校验表名防注入；没有状态列时无法停用，会明确报错。
  • 企业客服智能体示例：基于 Pydantic AI，固定策略（必须先调用检索工具、只依据返回内容回答、没有结果就拒答），记录每次检索，并生成事故。模型由环境变量选择，离线时使用确定性替身（不是语言模型）。
  • memwall 导入：把 memwall 扫描报告导入为 M6 发现，并导出记忆供其扫描。导入器按 memwall 0.6.1 的实际输出编写。

6　创新点

先说明边界：本项目的各个组成部分，现有开源项目大多已有某种形式的实现。我们声称的创新是组合与流程，而不是任何单项技术的首创。

序创新点内容与现有项目的关系
1条款版本与有效期作为基准按事故发生时间判定当时有效的条款版本与作用域，据此归因；来源更新触发影响分析与重新验证。agentmem、mneme、MemGuard（ac12644）有来源变化检测，但页面未写带有效期的版本判定。
2面向事故的完整流程六类根因分类；带审批和回滚的非破坏性修正；沿溯源图批量回归，并检查「修正前通过的题仍通过」。memory-blackbox 已有追溯、回滚与重跑；Ferryte 有 why --replay。审批流程与批量回归是本项目的组合点。
3面向历史库残留的删除验证探测范围含派生摘要与存储自带历史行；行为层让智能体回答探测问题；独立字节扫描作旁证；语义层降为提示。memwall、inspeximus、Ferryte 都有残留或删除检查。差异在于覆盖历史行与行为层的组合。
4真实堆栈上的可复现验证离线、确定性的默认模式；同一套流程在 Mem0、本地向量库、真实语言模型与真实嵌入模型上跑通，并记录失败与修复过程。——

在真实模型验证中，我们发现并修复了仿真无法暴露的缺陷：回归检查用死板的子字串比对，而真实模型会把「6笔」写成「6 笔」或「**6 笔**」，导致第一批 10 次运行中回归仅通过 6 次；修复比对方式后重新测量为 10 次全部通过（第 9 节）。

8　应用场景

8.1　场景一：产品条款更新后的智能体记忆过期（仿真）

  1. 事故：智能体回答「金卡免年费需要每年刷满 3 笔」，而现行条款（2026-07-01 起）是 6 笔；
  2. 调查：定位责任记忆（M1），同时发现一条依赖它的旧摘要，置信度来自溯源链接；
  3. 修正：预演展示「停用两条旧记忆、新增一条现行版本」；经审批后应用；
  4. 验证：重放原问题得到 6 笔；批量回归其他题没有退化；审计链完整；
  5. 输出：含记忆原文、条款原文、版本、修正前后快照校验值的证据报告。

8.2　场景二：删除请求后的残留（仿真，真实记忆库）

  1. 用 Mem0 自带的删除接口删除原始手机号记录；
  2. 探测：精确层在历史行中找到号码，变形层在「138 0000 0000」的摘要中找到，行为层发现智能体被问到时说出了号码；
  3. 修正：删除摘要，并清除历史行后压缩数据库文件；
  4. 验证：探测通过，智能体不再说出；另用独立的原始字节扫描确认数据目录中不再含目标。

8.3　可延伸的使用方式

方式说明
上线前验收在持续集成中运行体检与回归，作为智能体记忆变更的放行依据。
来源更新后巡检制度或条款发布新版本后运行体检，找出仍依赖旧版本的记忆。
个人信息删除核验对删除请求做多层探测并保留带校验的证据，不记录被删内容。
事故复盘从一次错误回答出发，得到责任记忆、证据与可审批的修正方案。

以上均为使用方式的设想；本项目尚未在任何真实企业系统中部署，也没有真实客户。

9　验证与数据

读数前提：基准用例由项目维护者自行设计，事故回答由有问题的记忆脚本化生成；真实模型验证样本很小。这些数字说明流程在这些情形下能走通，不代表真实环境的准确率。所有数字由仓库中的命令与记录文件产生。

9.2　真实堆栈验证（2026-10-20）

记忆库为 Mem0 2.2.1 加本地 Qdrant；智能体为 Pydantic AI；语言模型为 DeepSeek deepseek-chat；嵌入模型为 BAAI/bge-small-zh-v1.5（经 Mem0 的 fastembed 嵌入器）。每次运行使用全新的记忆库目录。

批次与场景结果
条款过期，10 次，离线哈希嵌入，修复前事故重现、归因、重放均为 10/10；回归 6/10（4 次失败均为检查方式缺陷）
条款过期，10 次，离线哈希嵌入，修复后事故重现、归因、重放、回归均为 10/10
删除残留，5 次，离线哈希嵌入修正前探测发现残留 5/5（其中真实模型说出手机号 5/5）；修正后探测通过、模型不再说出、原始字节不含目标均为 5/5
条款过期，10 次，真实嵌入模型事故重现、归因、重放、回归均为 10/10
删除残留，5 次，真实嵌入模型同上，均为 5/5

观察：真实模型会自行改写检索查询，使取回的三条记忆出现不同排序（10 次运行中出现 3 种），归因与修正在各种排序下都成立。修复回归比对是在看到第一批失败之后做的，第二批是修复后的重新测量，不是对同一批结果的重新判分。完整记录见仓库 benchmark/REAL_MODEL_RUNS.md。

9.3　已知限制（如实）

  • 所有数据为仿真示例，没有接入任何真实企业系统；
  • 真实模型验证只覆盖 M1 与 M5，只用了一个模型和一个嵌入模型，每个场景 5 到 10 次，模型输出有随机性；
  • M2、M3、M4、M6 只在仿真基准中验证；M6 仅为基础启发式；
  • 主张抽取目前只认「关键词 + 数字 + 单位」（支持中文数字到 999），不处理更复杂的表述；
  • 溯源链接的语义相似度阈值（0.2）是未经验证的起始值；
  • Mem0 适配器每次读取都获取全部记忆（上限 10000 条），只适合小规模数据；
  • 原始字节扫描只覆盖本次工作目录，SQLite 空闲页是否残留取决于具体构建，不构成通用保证；
  • Letta 适配器未实现：其本地服务端在验证环境中无法启动，我们不交付未经实际运行的适配器；
  • Docker 映像由 GitHub 持续集成构建并运行演示，作者本地环境没有 Docker 服务。

风险对策
与已有项目功能重叠，被认为重复造轮子逐项核实并如实列出对方已有能力（第 7 节）；创新点表述为组合与流程；与 memwall 互补而不重做扫描。

上游接口变动（Mem0、Letta 等）适配器隔离；参考实现不依赖外部框架；固定并记录验证过的版本。
